# 测试数据字段映射审核（规范 v1.0 ↔ SQLite schema 0001）

**审核对象**

- 需求侧：`docs/测试数据构建规范.md`（下称「规范」）
- 权威侧：`migrations/0001_init.sql`（下称「schema」，已冻结，是唯一真源）
- 运行侧：`data/ecommerce_support.db`（由 `go run ./cmd/seed -reset` 按本审核结论生成，当前规模见第 7 节）

**结论**

1. schema 与规范**字段级不重合**：规范的 24 张实体表里，schema 只有 19 张可直接对应；规范描述的约 40 个字段在 schema 中**没有列**（`is_test`、`source_type`、`sequence_no`、`cost_price_cents`、`reserved_qty`、`warranty_months`、`is_customized` 等）。本次**不新增列、不改 schema**，全部通过「现有列 + `attributes_json`/`metadata_json`/业务号命名」表达，无法表达的在第 5 节单列。
2. 规范的**枚举比 schema 宽**：支付状态、售后状态、售后类型、订单状态共 4 处出现 schema CHECK 不接受的取值，必须做**有损但有语义**的降级映射（第 3 节）。直接照抄规范会在 `INSERT` 阶段被 CHECK 约束打回。
3. 规范中「订单状态分布」的 9 个业务态，schema 只有 7 个 `order_status`。其中「支付失败 / 支付待确认 / 预售待尾款 / 派送中 / 退货退款完成」都不是订单态，必须**由支付表 + 物流表 + 售后表派生**，不能塞进 `order_status`（第 3.4 节）。这是最容易造出「已取消订单仍在派送」这类矛盾的根因。
4. 规范要求的「所有用户 `is_test=true`」在 schema 无列。本次以**数据集级标记**（`manifest.json`）+ 明显的合成号段（手机 `138000000xx`、邮箱 `*.example.test`、地址「测试市/模拟路」）替代，并在 `customers.status` 之外不做伪列。

## 1. 权威顺序与冲突处理原则

| 优先级 | 来源 | 处理 |
|---|---|---|
| 1 | `migrations/0001_init.sql` | 列名、类型、CHECK 枚举、外键一律以此为准 |
| 2 | 规范的业务语义 | 语义保留，载体可以是 JSON 列或派生规则 |
| 3 | 规范的字面字段名 | 若 schema 无列，写入 JSON 属性，字段名保持不变 |

不允许的做法（本次全部规避）：新增列、放宽 CHECK、把 `is_synthetic` 之类的标记塞进 `status`、用自由文本顶替枚举。

## 3. 枚举冲突与降级映射（**必须按此落库**）

### 3.1 支付状态

schema CHECK：`pending | succeeded | failed | closed | partially_refunded | refunded`

| 规范取值 | 落库值 | 语义保留方式 |
|---|---|---|
| `created` | `pending` | 记录已创建但未扣款，`paid_at` 为空 |
| `reversed` | `closed` | 重复扣款的待冲正那一笔；`provider_transaction_ref` 加 `-REVERSAL-PENDING` 后缀说明 |
| `succeeded` / `failed` / `partially_refunded` / `refunded` | 同名 | 直接映射 |

> 组合支付：一笔订单拆成 2 条渠道级支付行（如 `wechat_pay` + `account_balance`），金额之和等于订单实付；另有 1 单用单条 `mixed` 聚合行，用于覆盖「只看到组合支付、看不到拆分」的展示分支。**两笔拆分不能同时再写一条 `mixed` 合计行**，否则支付金额求和翻倍。

### 3.2 售后单状态

schema CHECK：`submitted | pending_review | approved | rejected | awaiting_customer | awaiting_return_shipment | processing | completed | cancelled`

| 规范取值 | 落库值 | 说明 |
|---|---|---|
| `draft` | `submitted` | schema 无草稿态，测试数据不生成草稿 |
| `shipping_back`（退货在途） | `awaiting_return_shipment` | 用 `order_item_id` + 退件包裹表达「已寄出」 |
| `received_by_merchant`（商家已收货） | `processing` | 质检中即处理中，`resolution` 写明「仓库已签收，质检中」 |

### 3.3 售后单类型

schema CHECK：`return | exchange | repair | refund | reship | price_protection`

| 规范取值 | 落库策略 |
|---|---|
| `refund_only`（仅退款） | `case_type='refund'` + `reason_code='refund_only'`，不生成退件包裹 |
| `logistics_intercept`（物流拦截） | `case_type='refund'` + `reason_code='logistics_intercept'`；拦截动作由 `shipments.shipment_status='intercepted'` + `event_code='intercepted'` 表达 |
| `invoice_change`（改开票信息） | 不进 `service_cases`（会破坏 CHECK），改走 `service_tickets(ticket_type='other', category='invoice_change')` |
| `return/exchange/repair/refund/reship/price_protection` | 同名直接映射 |

### 3.4 订单状态（规范 9 个业务态 → schema 7 个 `order_status`）

| 规范业务态 | `order_status` | 派生载体（关键，防止状态矛盾） |
|---|---|---|
| 待付款 | `pending_payment` | 无成功支付行，`paid_at IS NULL` |
| 支付失败 / 待确认 | `pending_payment` | `payments.payment_status='failed'` 或 `'pending'`，`paid_at` 为空 |
| 待发货 | `paid` 或 `processing` | 成功支付行金额 = 实付，无揽收轨迹 |
| 预售待尾款 | `pending_payment` + `is_presale=1` | 定金行 `succeeded`、尾款行 `pending`；`paid_amount_minor` = 定金（允许 ≠ 应付） |
| 已发货/运输中 | `shipped` | 包裹 `picked_up/in_transit/delivering` |
| 派送中 / 配送失败 | `shipped` | 包裹 `delivering` / `delivery_failed`，**订单态不单独设** |
| 已签收 | `completed` | 包裹 `delivered`，`delivered_at`/`completed_at` 均非空 |
| 已取消 | `cancelled` | `cancelled_at` 非空；若有包裹必须为 `intercepted`/`returned` 且轨迹含拦截节点 |
| 退货退款完成 | `completed`（部分退）或 `closed`（全额退清） | `refunded_amount_minor` > 0 且售后单 `completed` |

### 3.5 物流状态

schema CHECK 内已覆盖规范所需，只有「拦截申请中」没有对应状态：落为 `in_transit` 包裹里的一条 informational 事件（`event_code='intercept_requested'`），拦截成功才改 `shipment_status='intercepted'`。

### 3.6 发票状态

规范「开票失败」→ `rejected`；「红冲」→ `red_flushed`（原票），重开票另起一条 `issued` 记录，`invoice_no` 加 `-R1` 后缀做弱关联（schema 无 `red_flush_of` 列）。

## 4. 规范字段 → schema 载体对照（schema 无列者）

| 规范字段 | 载体 | 示例 |
|---|---|---|
| `warranty_months` / `return_policy_code` / `is_customized` / `is_perishable` / `cold_chain_required` / `invoice_supported` / `price_protection_supported` | `products.attributes_json` | `"return_policy_code":"customized_no_return"` |
| `source_type` / `source_url` / `source_checked_at` / `is_synthetic` / `price_type` | `products.attributes_json` | 全部为 `synthetic`，`source_url` 留空不伪造链接 |
| `cost_price_cents` / `reserved_qty` | **不生成** | schema 无列，且成本价不应进入演示库 |
| `is_test`（用户） | `manifest.json` 数据集级标记 + 合成号段 | 手机 `1380000xxxx`，邮箱 `userNNN@example.test` |
| `sequence_no`（消息） | `messages.created_at` 严格递增 + `metadata_json.seq` | 校验器按 `created_at, id` 校验单调 |
| `scenario_id` / `expected_outcome` / `risk_level` / `expected_tool_calls` | `testdata/scenarios/test_scenarios.jsonl` | 只做评测标注，**不注入模型上下文** |
| `shipment.direction`（正向/补发/退件） | `shipment_no` 前缀：`SHP-` / `SHP-B`（补发）/ `SHP-R`（退件） | schema 无方向列 |
| `refund.red_flush_of` / `invoice_change` | 命名后缀 + `service_cases.reason_code` | 见 3.3 / 3.6 |
| 价保「下单价/对比价/窗口」 | `promotions.rules_json` + `service_cases.resolution` | `resolution` 写明差额与依据 |
| 支付无订单（银行已扣款、下单失败） | **无法表达** | `payments.order_id NOT NULL`，见第 5 节 |

## 5. 无法表达 / 需要 migration 才能支持的项

| 项 | 原因 | 本次处理 |
|---|---|---|
| 支付成功但订单创建失败（孤立支付） | `payments.order_id NOT NULL REFERENCES orders` | 不生成；改由知识库文章 + 会话场景（转人工、人工核账）覆盖，**不伪造外键** |
| 组合支付的渠道级拆分退款明细 | `refunds` 无 `channel_split_json` | 拆分退款只落到 `payment_id`（单渠道）；`reason` 注明「组合支付按渠道比例退回」 |
| 发票与退款的直接关联 | `invoices` 无 `refund_id` | 通过同订单 + 时间先后 + `red_flushed` 状态表达 |
| 消息显式序号 | `messages` 无 `sequence_no` | `created_at` 单调 + `metadata_json.seq` |
| 商品成本价、库存预留 | 无列 | 不生成 |
| 用户 `is_test` 标记 | 无列 | `manifest.json` 声明全库合成 |
| 物流方向（正向/补发/退件） | 无列 | 业务号前缀约定 |

> 以上 7 项若要「列级」支持，需要新 migration（0002）；本次按规范第 10 节「协调 Agent」条款，**不擅自改 schema**，仅在此登记。

## 6. 一致性风险清单（生成器必须防住的矛盾）

除用户点名的 3 类（退款金额 > 订单金额、已签收仍在派送、售后单引用错误订单），本次额外识别并逐项加了守卫：

| 编号 | 风险 | 守卫方式 |
|---|---|---|
| M1 | 退款累计 > 可退余额（`paid - refunded`） | 退款金额由「行可退额 × 数量比例」推导，入库前断言累计 ≤ 上限 |
| M2 | `refunds` 的 `payment_id` 属于别的订单 | 只能从本单支付行里挑，校验器反查 `payments.order_id` |
| M3 | `orders.refunded_amount_minor` ≠ 成功退款之和 | 由退款成功事件单向累计，不允许手填 |
| M4 | 行折扣分摊后合计 ≠ 订单折扣（1 分钱对不上） | 最大余数法分摊，余数给金额最大的行 |
| M5 | 行实付合计 + 运费 ≠ 订单实付 | 同上，入库前断言 |
| M6 | 支付成功金额之和 ≠ 订单实付 | 支付行金额由「应付 - 已付」推导；失败/待冲正行不计入 |
| M7 | 包裹状态与最后一条轨迹不一致 | 状态由「最后一条状态型事件」反推，禁止手写 |
| M8 | 签收后又出现派送中（时间倒序） | 轨迹按时间轴单向追加，校验 `event_time` 严格递增 |
| M9 | 已取消订单仍在派送、且无拦截记录 | 取消前置条件：包裹必须 `pending`；否则必须先写拦截事件再取消 |
| M10 | `delivered_at` 为空但包裹已签收（或早于 `shipped_at`） | 由签收事件回填，校验时间链 `created ≤ paid ≤ shipped ≤ delivered ≤ completed` |
| M11 | 未支付订单却有成功支付/发票/发货 | 支付前置 `paid`，发货前置 `paid`，开票前置 `paid` |
| M12 | 预售单 `is_presale=0`，或尾款未付却已发货 | 预售必须 `is_presale=1` + 尾款 `pending`，且不发货 |
| M13 | `shipped` 订单没有包裹；`completed` 没有签收 | 状态迁移只能经由业务动作，禁止直接改 `order_status` |
| M14 | 售后单 `order_item_id` 不属于该订单 | 只能按下单时的行下标取，校验器反查 `order_items.order_id` |
| M15 | 售后单 `customer_id` 与订单客户不一致（串号） | 客户从订单取，不单独传参 |
| M16 | 申请数量 + 已退数量 > 购买数量 | 提交前算可用数量 |
| M17 | 同一行两个未终结售后单 | 已终结（completed/rejected/cancelled）才能再提 |
| M18 | 退款 `succeeded` 却无 `completed_at`；`failed` 却写 `completed_at` | 由状态强制回填/清空 |
| M19 | 退款被拒却增加了已退金额 | 只有 `succeeded` 参与累计 |
| M20 | 定制品/生鲜/贴身衣物走「无理由退货」并成功 | 商品 `return_policy_code` 决定可选售后类型，禁止违规成功案例 |
| M21 | 超过 7 天窗口却生成 `approved` 的无理由退货 | 售后申请时间 ≥ 签收 + 7 天的一律 `rejected`，`reason_code='out_of_window'` |
| M22 | 价保窗口 > 15 天却 `approved`；无降价活动却 `approved` | 价保单必须落在窗口内，且 `promotions.rules_json` 有对应差额 |
| M23 | 同一订单两次价保 | 一单一价保，校验唯一 |
| M24 | 发票金额 > 实付；已全额退款却仍 `issued` | 开票金额取开票时实付余额；全额退款后必须 `red_flushed` |
| M25 | 专票无税号、电子票无邮箱 | 按 `invoice_type` 必填校验 |
| M26 | 已开票却无订单、发票客户与订单客户不一致 | 由订单派生 |
| M27 | 退货寄回包裹被算作正向包裹（导致「全部签收」误判） | 包裹按 `SHP-R`/`SHP-B` 前缀区分方向 |
| M28 | 补发单没有补发包裹 | 补发 `approved/completed` 必须有 `SHP-B` 包裹 |
| M29 | 工具日志 `succeeded` 但业务记录不存在（幻觉） | 日志由真实业务行生成；拒绝/失败用 `failed`/`rejected` + `error_code` |
| M30 | 消息顺序错乱、`tool_call_id` 重复 | 会话内 `created_at` 严格递增；`tool_call_id` 全局唯一 |
| M31 | 待确认动作 `expires_at` < `created_at`；`executed` 无 `confirmed_at` | 由 TTL 推导；未确认不得执行 |
| M32 | 会话引用了别人订单（越权样本应为「拒绝」而非真数据） | 越权场景只写 `forbidden` 的工具失败日志 + 文案 |
| M33 | 库存 `status='out_of_stock'` 但 `stock_quantity>0` | 状态与库存互相推导 |
| M34 | 出现完整手机号/真实地址/真实运单号 | 全部脱敏 + `MOCK` 运单号 + 虚构地址 |
| M35 | 未来时间（除预计送达/预约送达/过期时间） | 所有业务时间 ≤ 数据锚点 |
| M36 | 一单多包裹时状态组合与订单态矛盾 | 订单 `completed` 要求所有正向包裹 `delivered` |
| M37 | 生鲜冷链单无冷链节点 | `cold_chain_required` 商品的包裹必须有冷链事件 |
| M38 | 退款金额为 0 或负数、部分退款金额超过行实付 | 金额下限 1 分，上限行实付 |

校验器把上述风险落成 40+ 类断言（`internal/seed/validate.go`，按行展开后实际执行 **14724 项**内存断言 + **14 项**落库 SQL 校验），**任一条不通过则整批不入库**，命令行返回非零退出码。
